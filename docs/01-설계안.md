# 업무자료 AI 도우미 — 설계안

작성 2026-09-09 · **개정 2026-09-09 (검토 반영, 확정)** · 대상 v0.1 MVP

> 이 문서가 **기준 문서**입니다. 설계가 바뀌면 여기를 먼저 고칩니다.
> 확정된 결정은 12장에 모아 두었습니다.

## 0. 한 줄 요약

**PDF 를 앱 폴더로 복사해 두고, pdf.js 로 페이지·글자 위치까지 붙잡아 쪼갠 뒤,
SQLite 안에서 키워드 검색과 벡터 검색을 함께 돌려 근거를 고르고, Ollama 의 로컬
모델에게 "이 근거만 읽고 답하라"고 시킨 다음, 답에 붙은 인용을 프로그램이 다시
검사한다.** 근거를 못 찾으면 답을 만들지 않고 못 찾았다고 말한다.

그리고 **AI 모델이 없어도 앱은 온전히 실행되고, 자료 등록·원문 보기·키워드
검색까지는 그대로 된다.** AI 는 얹는 것이지 전제가 아니다.

기존 두 앱(보결 배정 시스템 · 방과후 통합 매니저)과 같은 뼈대를 씁니다.
Tauri 2 + React + TypeScript + rusqlite, 자료는 `%APPDATA%`, 릴리스는 태그 하나.

## 1. 요구사항 분석 — 이 프로그램의 진짜 어려움

요구사항 14개 원칙 중에서 실제로 구현 난이도를 결정하는 것은 네 가지입니다.

### 1-1. "근거를 정확히 표시한다"가 가장 어렵다

AI 답변을 만드는 것보다 **"이 문장은 이 파일 18쪽의 이 문단에서 나왔다"를 틀리지
않게 유지하는 것**이 훨씬 어렵습니다. 텍스트를 추출하고 → 쪼개고 → 검색하고 →
LLM 에 넘기고 → 답을 받는 다섯 단계를 거치는 동안 위치 정보가 계속 흐려지기
때문입니다.

그래서 이 설계의 중심 원칙은 하나입니다.

> **텍스트를 추출한 그 순간부터 답변 화면까지, 원본 PDF 안의 문자 위치를
> 한 번도 잃어버리지 않는다.**

이걸 지키려고 2-1 에서 "추출과 보기를 같은 엔진(pdf.js)으로 한다"는 결정을
합니다. 다른 대부분의 설계 결정이 여기서 파생됩니다.

### 1-2. "환각을 막는다"는 프롬프트만으로는 안 된다

"근거에 없으면 답하지 마"라고 시키는 것은 필요하지만 충분하지 않습니다.
4B 급 로컬 모델은 특히 잘 어깁니다. 그래서 **프로그램이 답을 검사하는 층**을
따로 둡니다 (5-4).

다만 그 검증층이 무엇을 보장하고 무엇을 보장하지 못하는지를 **사용자에게 정확히
전달하는 것**이 검증 자체만큼 중요합니다. 부분 검증을 전체 검증인 것처럼 보여
주면, 없느니만 못합니다 (5-5).

### 1-3. "저사양 학교 PC에서 돈다"가 기술 선택을 지배한다

학교 행정용 PC 는 RAM 8GB 인 경우가 흔합니다. 여기서 LLM 과 임베딩 모델을
같이 돌리면 빠듯합니다. 그래서:

- 검색 쪽은 **가벼운 기술만** 씁니다. 벡터 인덱스(HNSW 등) 없이 단순 전수 계산.
- 모델은 갈아 끼울 수 있게 하고, 사양에 따라 다른 것을 권합니다.
- **LLM 없이 근거만 찾는 화면**을 따로 둡니다.

### 1-4. AI 는 선택 기능이어야 한다

첫 실행에 5GB 를 내려받아야 하는 프로그램은, 그 다운로드가 실패했을 때
**아무것도 못 하는 프로그램이 되어서는 안 됩니다.** 학교 네트워크·폐쇄망·용량
부족은 흔한 일입니다.

그래서 이 프로그램은 세 단계로 동작합니다 (2-12).

| 단계 | 필요한 것 | 되는 것 |
|---|---|---|
| **1. 자료 관리** | 아무것도 필요 없음 | 자료집, PDF 등록, 텍스트 추출, 원문 보기, **키워드 검색** |
| **2. 정밀 검색** | + 임베딩 모델 (약 1.2GB) | 하이브리드 검색, 뜻으로 찾기 |
| **3. AI 답변** | + 답변 모델 (약 3.3GB) | 답변 생성, 규정 해석, 문서 초안 |

**설치 실패가 앱 실행 실패로 이어지지 않습니다.**

## 2. 기술적 위험요소 검토

### 2-1. PDF 페이지 번호를 근거와 정확히 연결하는 방법

**결론: 텍스트 추출과 원문 보기를 둘 다 pdf.js 로 한다. 프론트엔드(WebView)에서.**

| 방법 | 한국어 | 좌표 | 부담 | 판정 |
|---|---|---|---|---|
| Rust `pdf-extract` | CID 폰트에서 깨짐 | 없음 | 가벼움 | ✗ |
| Rust `pdfium-render` | 좋음 | 글자 단위 | DLL 약 10MB 동봉 | △ |
| **pdf.js (프론트)** | **좋음** | **항목 단위 + 변환행렬** | 번들 약 3MB | **✓** |

결정적인 이유는 품질이 아니라 **일관성**입니다. 추출 엔진과 보기 엔진이 다르면
"18쪽"이라고 저장해 둔 위치와 실제로 열리는 화면이 어긋날 수 있습니다. 같은
엔진이면 어긋날 여지 자체가 없습니다. `getTextContent()` 가 준 항목 순서 그대로
텍스트를 이어 붙이고, 각 글자의 문자 오프셋을 항목 인덱스에 대응시켜 두면,
나중에 "이 청크의 3번째 문장"을 다시 화면 사각형으로 되돌릴 수 있습니다.

저장하는 것:

```
document 1건 → page N건 → 각 page: { text, item_offsets[] }
chunk 1건   → { page_start, page_end }
chunk_span  → 청크가 페이지를 걸칠 때, 페이지별 정확한 문자 구간
```

**쪽 번호의 두 가지 문제**

1. *물리 쪽 ≠ 인쇄된 쪽.* 표지·목차 때문에 PDF 12번째 장에 "8"이 찍혀 있곤
   합니다. MVP 는 **물리 쪽을 기준**으로 합니다 (원문 보기가 정확히 그리로 가야
   하므로). pdf.js 의 `getPageLabels()` 가 있는 문서는 둘 다 보여 줍니다
   (`8쪽 (문서 12/120)`). 머리말·꼬리말에서 쪽번호를 정규식으로 추정하는 것은
   v0.2 로 미룹니다 — 틀리면 오히려 해롭습니다.
2. *청크가 쪽을 걸칠 때.* `chunk_span` 으로 해결합니다. 인용은 **실제로 매칭된
   문장이 있는 쪽**을 씁니다. 두 쪽에 걸치면 `18~19쪽`.

**작업 부담:** 추출이 WebView 에서 돌아 UI 가 멈출 수 있습니다. pdf.js 가 제공하는
워커(`pdf.worker.mjs`)에서 돌리고, 페이지 단위로 진행률을 올리고, 취소 가능하게
합니다.

### 2-2. 표(表) 형태 PDF

**결론: 완벽한 표 인식은 포기한다. 대신 (가) 줄을 무너뜨리지 않고 (나) 표를
쪼개지 않고 (다) 쪼갤 수밖에 없으면 머리행을 붙여 준다. 그리고 언제나
원문 보기로 사용자가 직접 확인하게 한다.**

학교 자료는 표가 많습니다(단가표, 대상 기준표, 일정표). 표는 RAG 가 가장 잘
망가지는 지점입니다. `50,000` 이라는 숫자만 청크에 들어가고 그게 어느 항목의
값인지가 빠지면, 모델은 자신 있게 틀린 답을 합니다. (이 문제는 5-5 의 숫자 검증
한계와 같은 뿌리입니다.)

MVP 에서 할 것:

1. **줄 재구성.** pdf.js 항목들을 y 좌표로 묶고(±2pt), x 로 정렬해 한 줄로
   만듭니다. x 간격이 임계값(예: 평균 글자폭 × 2.5) 이상 벌어지면 탭을 넣습니다.
   대부분의 격자표가 `항목 ⇥ 대상 ⇥ 금액` 꼴로 살아납니다.
2. **표 블록 인식.** 탭 개수가 같은 줄이 3줄 이상 연속되면 하나의 표 블록.
3. **표는 쪼개지 않는다.** 표 블록이 청크 한도보다 작으면 통째로 한 청크.
4. **머리행 물려주기.** 한도를 넘어 쪼갤 때, 각 조각 앞에 첫 줄(머리행)을 다시
   붙입니다. 표 RAG 에서 가장 값싸고 효과 큰 조치입니다.

**정직하게 못 하는 것:** 병합 셀, 여러 줄 셀, 세로쓰기 표, 표 안의 표. 여기서는
줄이 뒤섞입니다. 그래서 **원문 보기가 안전망**이고, 그래서 이 프로젝트에서
근거 표시가 부가 기능이 아니라 핵심 기능입니다.

v0.2: pdf.js 의 연산자 목록(`getOperatorList`)에서 선 그리기 명령을 뽑아 실제
괘선 좌표로 열 경계를 잡으면 정확도가 크게 오릅니다.

### 2-3. 스캔 PDF

**결론: MVP 는 OCR 하지 않는다. 대신 스캔본을 반드시 감지해서 사용자에게 알린다.**

가장 나쁜 결과는 "스캔본이라 글자가 하나도 안 들어갔는데 조용히 등록 완료"입니다.
사용자는 자료를 넣었다고 믿고, 프로그램은 "자료에 없습니다"라고 답합니다.
이건 환각보다 더 위험합니다 — **틀린 안심**이기 때문입니다.

감지 규칙: 한 쪽에서 뽑힌 글자가 50자 미만이면서 그 쪽에 큰 이미지가 있으면
스캔 쪽. 문서의 스캔 쪽 비율이 30%를 넘으면 문서 상태를 `scanned` 로 표시하고
자료 목록에 배지를 답니다.

> ⚠ 이 문서는 글자를 읽을 수 없는 스캔본입니다. 검색되지 않습니다.

v0.2 선택지:
- **Windows 내장 OCR** (`Windows.Media.Ocr`, 한국어 언어팩). 추가 다운로드 0,
  이미 PC 에 있음. 학교 공문 스캔에 충분. 이쪽을 권합니다.
- Tesseract + `kor.traineddata` 동봉(약 15MB). 이식성은 좋지만 무겁습니다.

### 2-4. 한국어 chunk 분할

**결론: 토큰이 아니라 글자 기준. 목표 700자, 겹침 150자. 계층적으로 쪼갠다.**

토큰 기준으로 하려면 모델별 토크나이저가 필요합니다. 모델을 갈아 끼울 수 있게
하는 것이 요구사항이므로, 모델에 의존하지 않는 글자 기준이 맞습니다. 한국어는
대략 1자 ≈ 0.7~1.2 토큰이라 700자면 bge-m3 의 8K 창에 여유롭게 들어갑니다.

쪼개는 순서(위에서부터 시도, 안 되면 아래로):

1. **제목 경계** — `제○장`, `제○조`, `○○. `, `가. 나. 다.`, `①②③`, `Ⅰ. Ⅱ.`,
   `【 】`, 굵은 큰 글씨 줄.
2. **문단** — 빈 줄.
3. **문장** — 종결 어미 + 마침표: `다.` `요.` `음.` `임.` `함.` `것.` 그리고 `?` `!`
4. **강제 절단** — 한도 초과 시.

> **한국어 함정:** `.` 만 보고 문장을 끊으면 안 됩니다. `1.` `제3조.`
> `2026. 3. 1.` `○○교육청.` 은 문장 끝이 아닙니다. 숫자 뒤 마침표, 한 글자 뒤
> 마침표, 날짜 패턴은 예외 처리해야 합니다. 순수 함수라 단위 테스트하기 쉽습니다.

**문맥 머리말.** 각 청크는 자기 위치를 `heading_path` 로 함께 저장합니다.

```
2026 늘봄학교 운영 매뉴얼 > Ⅲ. 프로그램 운영 > 3. 강사 채용
```

검색용 텍스트와 LLM 에 넘길 때는 **앞에 붙이고**, 근거로 화면에 보여 줄 때는
**빼고** 원문만 보여 줍니다.

### 2-5. Hybrid Search 가 필요한가

**결론: 반드시 필요하다. 그리고 키워드 검색은 임베딩 없이도 되므로,
"AI 없이 되는 검색"의 토대가 된다 (2-12).**

업무자료 질문에는 결정적인 문자열이 들어갑니다 — `초3 이용권`, `제7조`,
`2026학년도`, `자유수강권`, `10만원`. 벡터 검색은 이런 걸 뭉갭니다. "초3"과
"초4"의 임베딩은 거의 같습니다. 반대로 키워드만 쓰면 "교재를 살 수 있나요"라는
질문이 "물품 구입 가능 항목"을 못 찾습니다. 둘 다 있어야 합니다.

**키워드: SQLite FTS5 + `trigram` 토크나이저**

한국어에서 `unicode61` 기본 토크나이저를 쓰면 조사 때문에 망합니다 —
`이용권을`, `이용권은`, `이용권이` 가 전부 다른 낱말이 됩니다. trigram 은 3글자
단위 부분 일치라 조사가 붙든 말든 걸립니다. 색인이 본문의 3~4배로 커지지만,
이 규모(문서 수백 개)에서는 문제가 아닙니다.

- 주의 1: trigram 은 **3글자 이상** 질의만 됩니다. 1~2글자 낱말은 벡터 쪽에
  맡기고, 임베딩이 없는 상태에서는 `LIKE` 로 대체합니다.
- 주의 2: 색인용으로 정규화한 별도 칼럼(`text_norm`)을 씁니다 — 전각→반각,
  연속 공백 정리, 줄바꿈 제거.
- rusqlite 의 `bundled` 는 FTS5 를 켜서 빌드하므로 추가 의존성이 없습니다.

**벡터: 인덱스 없이 전수 계산 (Rust)**

```
bge-m3 = 1024차원 × 4바이트 = 청크당 4KB
청크 20,000개 = 80MB → 메모리에 그냥 올린다
코사인 유사도 전수 계산 = 2,000만 곱셈 ≈ 10~20ms (단일 스레드)
```

**HNSW 도, sqlite-vec 도, 파이썬도, 별도 벡터 DB 도 필요 없습니다.**
임베딩은 SQLite BLOB 으로 두고, 자료집을 처음 검색할 때 메모리로 올려 캐시합니다.
혹시 10만 개를 넘기면 그때 `sqlite-vec` 를 얹으면 되고, 스키마는 그대로 씁니다.

**합치기: RRF (Reciprocal Rank Fusion)**

```
점수 = w_kw × 1/(60 + 키워드순위) + w_vec × 1/(60 + 벡터순위)
```

각각 상위 40개를 뽑아 합치고 상위 12개를 씁니다. 점수 정규화가 필요 없어서
안전합니다 — 특히 trigram 의 BM25 점수는 척도가 이상해서 순위만 쓰는 게 맞습니다.
가중치는 설정으로 빼 두고 실제 자료로 조정합니다(기본 0.5/0.5).
**임베딩이 없으면 `w_vec = 0` 이 되어 자연스럽게 키워드 전용으로 떨어집니다.**

**이웃 확장.** 청크가 뽑히면 같은 문서의 앞뒤 청크(±1)를 같이 가져와 문맥을
복원합니다. 값싸고 답변 품질이 확 오릅니다. 재순위(rerank) 모델은 MVP 에
넣지 않습니다.

### 2-6. 임베딩 모델

**결론: `bge-m3` (Ollama) 기본. 1024차원, 약 1.2GB, 8K 창. 교체 가능.**

한국어를 포함한 100개 이상 언어로 학습됐고, 긴 문서에 강하고, 밀집·희소 검색을
함께 염두에 두고 만들어진 모델입니다. `nomic-embed-text` 가 더 유명하지만 영어
중심이라 여기서는 부적합합니다. 저사양 대안으로 `paraphrase-multilingual`
(278M, 768차원)을 설정에서 고를 수 있게 합니다.

> **중요 — 모델을 바꾸면 전부 다시 색인해야 합니다.** 다른 모델의 벡터를 한
> 자료집에 섞으면 검색이 조용히 망가집니다. 자료집 행에 `embed_model`/`embed_dim`
> 을 저장하고, 불일치를 발견하면 벡터 검색을 막고 (키워드 검색은 계속 됩니다)
> "재색인이 필요합니다"라고 알립니다. 재색인은 사용자 동의를 받고, 진행률을
> 보여 주고, 취소할 수 있게 합니다.

### 2-7. LLM 을 검색된 근거에만 묶는 방법

네 겹으로 막습니다. 하나만으로는 부족합니다.

**① 프롬프트 (필요조건)**

```
당신은 학교 업무 담당자를 돕는 도우미입니다.
아래 [근거] 안에 있는 내용만 사용해 답하십시오.

- 근거에 없는 내용은 절대 쓰지 마십시오. 일반 상식으로 채우지 마십시오.
- 근거로 답할 수 없으면 정확히 이렇게만 답하십시오:
  "등록된 자료에서 해당 내용을 확인할 수 없습니다."
- 모든 문장 끝에 근거 번호를 [1] 처럼 붙이십시오.
- 자료에 적힌 사실과 당신의 실무 해석을 반드시 구분하십시오.

[근거]
[1] 2026 늘봄학교 운영 매뉴얼 > Ⅲ. 프로그램 운영 (18쪽)
"…원문…"
[2] …
```

`temperature 0.1`, 그리고 구조가 필요한 기능은 Ollama 의 `format` 으로 JSON
스키마를 강제합니다.

**② 근거 번호 강제와 파싱**

답변에서 `[n]` 을 뽑아냅니다. 존재하지 않는 번호를 인용하면 그 문장에 경고를
답니다. 인용이 하나도 없으면 답변 전체를 보류합니다.

**③ 근거 대조 검사 (프로그램이 한다)** → 자세한 내용과 **그 한계**는 5-4, 5-5.

**④ 답하지 않는 기준 (거부 임계값)**

LLM 을 부르기 *전에* 판단합니다.

| 상황 | 처리 |
|---|---|
| 최고 코사인 < 0.35 **이고** 키워드 히트 0건 | **LLM 호출 안 함.** "관련 자료를 찾지 못했습니다" + 그래도 본 상위 후보 목록 제시 |
| 최고 코사인 0.35 ~ 0.50 | 답변하되 "근거가 약합니다" 경고 |
| 그 이상 | 정상 |

> 이 숫자들은 **아직 근거 없는 초기값**입니다. 실제 학교 자료로 재는 절차를
> P4b 에 넣어 두었습니다(10-2 골든 셋). 하드코딩하지 않고 설정에 둡니다.

후보 목록을 항상 보여 주는 것이 중요합니다. "못 찾았습니다"만 나오면 사용자는
프로그램을 못 믿게 되지만, "이런 것들을 봤는데 관련이 없어 보입니다"는 판단을
사용자에게 돌려줍니다.

### 2-8. 근거가 서로 충돌할 때

**원칙: AI 가 몰래 하나를 고르지 않는다. 둘 다 보여 주고 다르다고 말한다.**

감지: 상위 근거가 서로 다른 문서에서 왔고, 질문 키워드 주변의 숫자/조건이
서로 다를 때. (완전한 감지는 어렵지만, 숫자 불일치만 잡아도 실무의 대부분입니다.)

> ⚠ 자료에 따라 내용이 다릅니다. 확인이 필요합니다.
>
> | 자료 | 발행 | 내용 |
> |---|---|---|
> | 2025 운영지침 p.12 | 2025-02 | 1인당 5만원 |
> | 2026 운영지침 p.14 | 2026-02 | 1인당 6만원 |

**우선순위는 자동 적용하지 않고 힌트만 줍니다.** 자료 등록 시 `발행일`,
`발행기관`(교육청/학교/기타), `적용연도`를 받아 두면 "최신 자료는 2026 운영지침
입니다" 같은 안내를 붙일 수 있습니다. 하지만 자동으로 옛 자료를 버리지는
않습니다 — 학교 업무에서는 옛 지침이 여전히 유효한 경우가 있습니다.

### 2-9. AI 모델 설치 UX — 설명 먼저, 동의 뒤에 다운로드

**원칙: 앱을 처음 켰을 때 설명 없이 아무것도 내려받지 않는다.**

첫 실행 마법사는 자료집 만들기까지만 하고 끝납니다. AI 는 그 다음 화면에서,
아래 안내를 보여 준 뒤 **사용자가 버튼을 눌러야** 시작합니다.

```
┌──────────────────────────────────────────────────────┐
│  AI 기능을 사용하려면 로컬 AI 모델 설치가 필요합니다. │
│                                                      │
│  약 5GB 의 저장 공간과 최초 1회의 인터넷 연결이       │
│  필요합니다. 설치된 모델과 등록 문서는 이후 로컬      │
│  환경에서 사용할 수 있습니다.                         │
│                                                      │
│  ─ 지금 설치하지 않아도 다음 기능은 사용할 수 있습니다 │
│    · 자료집 관리                                      │
│    · PDF 등록 및 원문 보기                            │
│    · 낱말로 찾기(키워드 검색)                         │
│                                                      │
│           [ AI 모델 설치 ]    [ 나중에 설치 ]         │
└──────────────────────────────────────────────────────┘
```

[나중에 설치] 를 누르면 앱은 그대로 쓸 수 있고, 설정 화면과 AI 메뉴에
"AI 모델 설치" 버튼이 남습니다. 다시 묻지 않습니다.

**설치를 고르면 나오는 단계별 화면**

| 상태 | 화면 |
|---|---|
| Ollama 미설치 | 공식 사이트 링크 + `winget install Ollama.Ollama` 복사 버튼 + [다시 확인] |
| 설치됐으나 미실행 | "Ollama 를 실행해 주세요" + 실행 방법 |
| 실행 중, 모델 없음 | 모델별로 크기·용도를 보여 주고 개별 [받기] → `POST /api/pull` 스트리밍 진행률 |
| 정상 | 통과 |

**모델을 따로따로 받게 합니다.** 검색용(약 1.2GB)만 받아도 정밀 검색이 되고,
답변용(약 3.3GB)은 나중에 받아도 됩니다. 5GB 를 한 덩어리로 요구하지 않습니다.

- **앱이 Ollama 설치 프로그램을 몰래 받아 실행하지는 않습니다.** 권한·신뢰
  문제도 있고, 학교 PC 정책에 걸릴 수도 있습니다. 안내와 복사 버튼까지가 적당.
- **모델 내려받기는 앱이 대신 해 줍니다** — 사용자가 버튼을 눌러 시작한 것이고,
  명령 프롬프트를 열게 하는 것보다 훨씬 낫습니다.
- 다운로드 중에도 앱의 다른 화면은 계속 쓸 수 있습니다(백그라운드 작업).
- 실패하면 실패한 이유를 보여 주고, **앱은 1단계 기능으로 계속 동작합니다.**

**폐쇄망 학교 대비:** 다른 PC 에서 모델을 받아 `%USERPROFILE%\.ollama\models`
폴더를 통째로 옮기는 방법을 안내 화면과 README 에 적어 둡니다.

### 2-10. 저사양 PC 대응과 모델 권장

**모델 이름을 코드에 박지 않습니다.** 설정에 후보 목록을 두고, 실제 목록은
Ollama 의 `/api/tags` 에서 읽어 고르게 합니다. 아래는 *권장값*일 뿐입니다.

첫 설정 때 **설치된 RAM 을 읽어 권장 조합을 제안**합니다 (MVP 에 넣습니다 —
Windows API 한 번 호출이라 값이 쌉니다).

| 감지된 RAM | 답변 모델 권장 | 임베딩 권장 | 표시 |
|---|---|---|---|
| 8GB 미만 | `gemma3:4b` | `paraphrase-multilingual` | "이 PC 에서는 가벼운 모델을 권합니다" |
| 8 ~ 15GB | `gemma3:4b` | `bge-m3` | 기본 |
| 16GB 이상 | `qwen3:8b` | `bge-m3` | "이 PC 는 더 좋은 모델을 쓸 수 있습니다" |

권장은 **제안일 뿐이고 사용자가 언제든 바꿉니다.** 설정 화면에서 모델을 바꾸면
답변 모델은 즉시 적용되고, 임베딩 모델은 재색인 동의를 물어봅니다 (2-6).

그 밖의 저사양 대응:

- **모델 상주 관리.** 8GB 에서 임베딩 모델과 LLM 이 동시에 메모리에 있으면
  빠듯합니다. Ollama 의 `keep_alive` 를 명시적으로 씁니다 — 색인 중에는 임베딩만
  붙잡고(`5m`), 색인이 끝나면 놓아 주고(`0`), 질의 때는 임베딩 → LLM 순서로
  호출합니다.
- **색인은 배치·취소 가능·진행률 표시.** 임베딩은 `/api/embed` 에 16~32개씩
  묶어 보냅니다. 300쪽 PDF 가 8GB PC 에서 수 분 걸립니다 — 정상이라고 화면에
  적어 둡니다.
- **답변은 스트리밍.** 첫 글자가 빨리 나오면 체감이 완전히 다릅니다.
- **[낱말로 찾기] 화면** — LLM 도 임베딩도 부르지 않는 검색 화면 (2-12).

### 2-11. 앱 업데이트 시 자료 보존

기존 두 앱에서 이미 검증된 방식을 그대로 씁니다.

- 자료는 **설치 폴더가 아니라** `%APPDATA%\kr.school.docaid\` 에.
- `PRAGMA user_version` 기반 전진 전용(forward-only) 마이그레이션, 트랜잭션 안에서.
- **마이그레이션 직전 자동 백업** — `backups\pre-migration-v{n}-{날짜}.db`.
  rusqlite 의 `backup` 기능은 이미 쓰고 있습니다.
- 실패하면 롤백하고 백업 위치를 알려 줍니다.
- **임베딩은 스키마 변경으로 절대 버리지 않습니다.** 다시 만드는 비용이 큽니다.
  임베딩 모델이 바뀔 때만, 그것도 사용자 동의를 받고 다시 만듭니다.
- 보결 앱의 `app:sandbox` 패턴을 그대로 도입 — identifier 를 바꿔 띄워 실제
  자료 없이 "자료를 지우는 시험"을 합니다.

### 2-12. AI 없이 동작하는 구조 ★ (검토 반영 · 새 항목)

요청하신 "AI 설치 실패가 앱 실행 실패로 이어지지 않는 구조"를 위해, **색인을
두 단계로 쪼갭니다.**

```
PDF 등록
  ├─ 1단계: 텍스트 색인   ← 모델 필요 없음. 항상 실행.
  │     추출 · 분할 · chunk · chunk_span · FTS5
  │     → 이 시점에 이미: 원문 보기 ✓  키워드 검색 ✓
  │
  └─ 2단계: 임베딩 색인   ← 임베딩 모델 필요. 나중에 해도 됨.
        /api/embed → embedding 테이블
        → 이 시점부터: 하이브리드 검색 ✓
```

**문서마다 `embed_state` 를 둡니다** (`none` / `partial` / `done`).
나중에 모델을 설치하면 설정 화면에 이렇게 뜹니다.

> 임베딩이 없는 문서가 12개 있습니다. [지금 만들기]  (약 4분 예상)

**검색 화면의 두 가지 모드**

| 모드 | 필요한 것 | 버튼 |
|---|---|---|
| 낱말로 찾기 | 없음 | `[낱말로 찾기]` — FTS5 trigram 만 |
| 뜻으로 찾기 | 임베딩 모델 | `[근거 찾기]` — 하이브리드 |
| AI 답변 | + 답변 모델 | `[질문하기]` |

쓸 수 없는 버튼은 **숨기지 않고 비활성으로 두고**, 왜 못 쓰는지와 어떻게 하면
쓸 수 있는지를 그 자리에 적습니다. 숨기면 사용자는 기능이 없다고 생각합니다.

> `[질문하기]`  ⓘ AI 모델이 설치되지 않았습니다. [설치 방법]

**Ollama 연결 상태는 앱 상태 표시줄에 항상 보이게** 둡니다
(`● AI 준비됨` / `○ AI 없음` / `◐ 모델 받는 중 63%`).

**실패해도 앱이 죽지 않게** — Ollama 호출은 전부 타임아웃(연결 2초, 생성 120초)
을 걸고, 실패는 화면의 오류 메시지로만 나타납니다. 앱 시작 경로에서 Ollama 를
기다리지 않습니다 (시작 시 비동기로 한 번 확인하고 말 뿐).

## 3. 권장 기술 스택

| 층 | 선택 | 이유 |
|---|---|---|
| 껍데기 | **Tauri 2** | 기존 두 앱과 동일. 설치 파일 작고, 관리자 권한 불필요, 업데이터 검증됨 |
| 화면 | **React 18 + TypeScript + react-router** | 동일 |
| PDF | **pdf.js** (번들, 워커, cMap 로컬) | 추출과 보기를 같은 엔진으로 (2-1) |
| 저장소 | **SQLite** (rusqlite, bundled) | 파일 하나. FTS5 포함. 백업 쉬움 |
| 키워드 검색 | **FTS5 trigram** | 한국어 조사 문제 회피. 모델 없이 동작 (2-5) |
| 벡터 검색 | **Rust 전수 계산** | 이 규모에서는 인덱스가 불필요 (2-5) |
| 임베딩 | **Ollama + bge-m3** (교체 가능) | 한국어·긴 문서 (2-6) |
| 답변 | **Ollama + gemma3:4b / qwen3:8b** (교체 가능) | 사양별 권장 (2-10) |

**새로 들어오는 의존성은 pdf.js 하나뿐입니다.**

**쓰지 않기로 한 것들** — LangChain/LlamaIndex(파이썬 런타임 동봉),
Chroma/Qdrant/LanceDB(별도 프로세스), sqlite-vec(지금 규모엔 불필요),
재순위 모델(저사양에서 값이 비쌈).

### 3-1. 이름 규칙 ★ (확정)

방과후 앱에서 **한글 `productName` 때문에 릴리스가 조용히 깨진 적이 있습니다**
(GitHub Release 가 첨부 파일 이름에서 한글을 떼어 내어 `latest.json` 의 url 과
어긋남). 그래서 규칙을 명시합니다.

| 자리 | 값 | 언어 |
|---|---|---|
| `productName` (tauri.conf.json) | `DocAid` | **영문** |
| Cargo `package.name` | `docaid` | **영문** |
| npm `name` | `docaid` | **영문** |
| bundle identifier | `kr.school.docaid` | **영문** |

```
        ↓ HTTP 127.0.0.1:11434  (없어도 앱은 돈다)
   Ollama → bge-m3 / gemma3:4b
```

**모델 교체 지점을 trait 두 개로 묶습니다** (요구사항 6·9).

```rust
#[async_trait]
trait EmbedProvider {
    fn model(&self) -> &str;
    fn dim(&self) -> usize;
    async fn embed(&self, texts: &[String]) -> Result<Vec<Vec<f32>>>;
}

#[async_trait]
trait LlmProvider {
    fn model(&self) -> &str;
    async fn generate(&self, req: GenerateRequest, tx: Sender<Delta>) -> Result<()>;
}
```

두 trait 은 **`Option` 으로 보유**합니다. 없으면 `None` 이고, 그 상태를 화면이
읽어 버튼을 비활성으로 만듭니다 (2-12). 외부 API 구현체를 나중에 만든다면
**기본 비활성**이고, 켤 때 "업무자료가 외부 서버로 전송됩니다"를 크게 경고합니다.

## 5. RAG 와 근거 추적 설계

### 5-1. 등록 파이프라인

```
파일 선택
  → 앱 폴더로 복사 (files/<doc_id>.pdf)   ※ 원본이 없어져도 원문 보기가 살아야 함
  → sha256 계산 → 중복/개정 판정
  → pdf.js 워커: 페이지별 텍스트 + 항목 오프셋
  → 스캔본 감지 → 표시
  → 줄 재구성 · 표 블록 인식
  → 계층 분할 (목표 700자 / 겹침 150자 / heading_path)
  → chunk · chunk_span · FTS5 저장          ─── 1단계 끝. 여기까지 모델 불필요
  ┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈
  → (임베딩 모델이 있으면) /api/embed 배치 → embedding 저장 → embed_state='done'
```

각 단계마다 진행률과 취소가 있습니다. 중간에 끊기면 그 문서만 `indexing` 으로
남고, 다시 등록하면 처음부터 다시 합니다(단순함 우선).

### 5-2. 질의 파이프라인

```
질문 + 자료집 선택
  → (임베딩 있으면) 질문 임베딩
  → 키워드 상위 40 (FTS5 trigram)   ─┐
  → 벡터 상위 40 (전수 코사인)      ─┴→ RRF 융합 → 상위 12
  → 이웃 확장 (±1 청크)
  → 거부 임계값 판정 ─── 미달 → LLM 호출 안 함, 후보만 표시
  → 근거 블록 조립 (번호 · 파일명 · heading_path · 쪽 · 원문)
  → LLM 스트리밍 생성
  → 인용 파싱 · 3-gram 대조 · 숫자 대조 (인용된 청크 범위 안에서만)
  → 충돌 감지
  → 화면: 답변 + 근거 카드 + 검증 결과 + [원문 보기]
  → 작업 기록 저장 (근거 원문 스냅샷 포함)
```

### 5-3. 근거 카드와 원문 보기

```
[답변]
초3 이용권으로 교재비를 사용할 수 있습니다. [1]
다만 학습 준비물에 해당하는 소모품은 제외됩니다. [1][2]

  ─ AI 해석 ────────────────────────────────
  실무에서는 교재 구입 시 영수증에 도서명이 나오도록 하고,
  준비물성 물품은 별도 예산으로 처리하는 편이 안전합니다.
  ※ 이 문단은 자료에 직접 적힌 내용이 아니라 AI 의 해석입니다.
  ──────────────────────────────────────────

[참고 근거]
① 2026 초3 이용권 운영지침 · 18쪽
   Ⅱ. 사용 범위 > 2. 사용 가능 항목
   "…교재비(도서 형태의 학습교재)는 사용 가능하며…"
   [원문 보기]
② 2026 초3 이용권 FAQ · 4쪽
   …
```

`[원문 보기]` 를 누르면 같은 화면 오른쪽에 pdf.js 뷰어가 열려 **해당 쪽으로
이동하고 해당 구간에 형광펜 사각형**을 칠합니다. `chunk_span` 의 문자 오프셋을
그 페이지의 `getTextContent()` 항목으로 되돌려 좌표를 얻습니다. 추출과 보기가
같은 엔진이라 어긋나지 않습니다 (2-1).

### 5-4. 검증층

| 검사 | 방법 | 범위 | 실패 시 |
|---|---|---|---|
| 인용 존재 | `[n]` 파싱 | 답변 전체 | 인용 0개면 답변 보류 |
| 인용 유효 | n 이 근거 번호 범위 안인가 | 답변 전체 | 해당 문장에 경고 |
| 내용 근접 | 문자 3-gram 포함율 | **그 문장이 인용한 청크** | "근거와의 연결이 약함" |
| 숫자 대조 | 숫자·금액·날짜·`제○조` 문자열 존재 | **그 문장이 인용한 청크** | 경고 (5-5 참고) |
| 근거 충분 | 코사인·키워드 임계값 | 검색 단계 | LLM 호출 자체를 안 함 |
| 근거 충돌 | 문서 간 숫자 불일치 | 상위 근거 | 나란히 표시 + 경고 |

**검증 범위는 "전체 검색 결과"가 아니라 "그 문장이 실제로 인용한 청크"입니다.**
검색 결과 12개 어딘가에 그 숫자가 있다는 것은 아무 의미가 없습니다. 답변이
`[1]` 이라고 인용했으면 1번 청크 안에서만 찾습니다.

이 층은 전부 **순수 함수**라 테스트하기 쉽습니다 (10-1).

### 5-5. 숫자 검증이 보장하는 것과 보장하지 못하는 것 ★ (검토 반영 · 새 항목)

**이 검증은 부분 검증입니다. 절대 전체 검증인 것처럼 표시하지 않습니다.**

숫자가 근거 안에 존재한다는 사실은 **그 숫자가 옳게 쓰였다는 뜻이 아닙니다.**
근거가 이렇다고 합시다.

```
A 대상: 25만원
B 대상: 50만원
```

AI 가 "A 대상은 50만원입니다"라고 잘못 답해도, `50만원` 이라는 문자열은 근거
안에 **실제로 존재합니다.** 현재 검증은 이걸 통과시킵니다.

**그래서 화면 문구를 이렇게 제한합니다.**

| ✗ 쓰지 않는 표현 | ✓ 쓰는 표현 |
|---|---|
| 답변 검증 완료 | **답변에 사용된 주요 숫자가 인용 근거에서 확인되었습니다.** |
| 정확한 답변입니다 | 확인된 숫자: `25만원`, `2026. 3. 1.`, `제7조` |
| ✅ 검증됨 | ⓘ 숫자가 **어떤 항목의 값인지**까지는 확인하지 못합니다. 표가 포함된 근거는 원문을 직접 확인해 주세요. |

실패했을 때만 강한 표현을 씁니다.

> 🔴 답변의 `60만원` 을 인용 근거에서 찾지 못했습니다. 원문을 확인해 주세요.

**즉, 이 검증은 "통과"를 신뢰의 근거로 주지 않고, "실패"를 경고의 근거로만
씁니다.** 통과는 그저 "적어도 지어낸 숫자는 아니다" 정도입니다.

**v0.2 확장 여지** (구조를 지금 열어 둡니다):

1. **문맥 창 대조** — 숫자가 존재하는지가 아니라, *질문의 대상어와 같은 줄 /
   같은 표 행 / 앞뒤 N자 안에* 있는지를 봅니다. 위 A/B 예시를 잡아냅니다.
2. **표 행 대조** — 청크가 `kind='table'` 이면 머리행과 행 머리를 파싱해
   `(행, 열) → 값` 으로 만들어 두고, 답변의 `대상=값` 쌍을 대조합니다.
3. **숫자 단위 정규화** — `50만원` / `500,000원` / `50만 원` 을 같은 값으로.

이를 위해 검증 결과를 **불리언이 아니라 구조체로** 저장합니다.

```rust
struct NumberCheck {
    literal: String,        // "50만원"
    found_in_chunk: Option<ChunkId>,
    char_offset: Option<usize>,   // v0.2 문맥 창 대조의 출발점
    context_verified: Option<bool>,  // v0.1 에서는 항상 None
}
```

`context_verified` 는 v0.1 에서 늘 `None` 이고, 화면은 이 값이 `None` 일 때
위 제한적 문구를 씁니다. v0.2 에서 이 필드를 채우면 화면 문구가 저절로
강해집니다. **필드를 지금 만들어 두는 것이 이 절의 목적입니다.**

### 스키마 초안 (v1)

```sql
PRAGMA user_version = 1;

CREATE TABLE collection (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE,
  embed_model TEXT,                   -- NULL = 아직 임베딩 없음 (2-12)
  embed_dim INTEGER,                  -- 섞이면 검색이 조용히 망가짐
  created_at TEXT NOT NULL
);

CREATE TABLE document (
  id INTEGER PRIMARY KEY,
  collection_id INTEGER NOT NULL REFERENCES collection(id),
  title TEXT NOT NULL,                -- 사용자가 고칠 수 있는 표시 이름
  filename TEXT NOT NULL,
  sha256 TEXT NOT NULL,
  byte_size INTEGER NOT NULL,
  page_count INTEGER NOT NULL,
  source_path TEXT,                   -- 등록 당시 원본 경로 (참고용)
  issuer TEXT,                        -- 교육청 / 학교 / 기타   <- 충돌 판단 힌트
  issued_at TEXT,                     -- 발행일                 <- 충돌 판단 힌트
  apply_year INTEGER,                 -- 적용연도
  status TEXT NOT NULL,               -- ok | scanned | extract_failed | indexing
  embed_state TEXT NOT NULL DEFAULT 'none',   -- none|partial|done  (2-12)
  revision_of INTEGER REFERENCES document(id),    -- 8번 요구사항: 버전 추적
  superseded_by INTEGER REFERENCES document(id),
  created_at TEXT NOT NULL
);

CREATE TABLE page (
  document_id INTEGER NOT NULL REFERENCES document(id),
  page INTEGER NOT NULL,              -- 1부터, 물리 쪽
  label TEXT,                         -- PDF 페이지 라벨 (있으면)
  text TEXT NOT NULL,
  is_scanned INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (document_id, page)
);

CREATE TABLE chunk (
  id INTEGER PRIMARY KEY,
  document_id INTEGER NOT NULL REFERENCES document(id),
  ord INTEGER NOT NULL,               -- 문서 안 순서 (이웃 확장용)
  heading_path TEXT,                  -- "Ⅲ. 프로그램 운영 > 3. 강사 채용"
  text TEXT NOT NULL,                 -- 화면에 보여 줄 원문
  text_norm TEXT NOT NULL,            -- FTS5 색인용 정규화본
  kind TEXT NOT NULL DEFAULT 'text',  -- text | table   (5-5 v0.2 확장 지점)
  page_start INTEGER NOT NULL,
  page_end INTEGER NOT NULL
);

CREATE TABLE chunk_span (             -- 쪽을 걸치는 청크의 정확한 위치
  chunk_id INTEGER NOT NULL REFERENCES chunk(id),
  page INTEGER NOT NULL,
  char_start INTEGER NOT NULL,        -- 그 페이지 text 안의 오프셋
  char_end INTEGER NOT NULL
);

CREATE TABLE embedding (
  chunk_id INTEGER PRIMARY KEY REFERENCES chunk(id),
  model TEXT NOT NULL,
  dim INTEGER NOT NULL,
  vec BLOB NOT NULL                   -- f32 리틀엔디언
);

CREATE VIRTUAL TABLE chunk_fts USING fts5(
  text_norm,
  content='chunk', content_rowid='id',
  tokenize='trigram'
);

-- 작업 기록 --------------------------------------------------------------
CREATE TABLE job (
  id INTEGER PRIMARY KEY,
  kind TEXT NOT NULL,                 -- search|interpret|draft|compare|summarize
  question TEXT NOT NULL,
  collections_json TEXT NOT NULL,     -- 여러 자료집 선택 대비 (요구사항 3)
  llm_model TEXT,                     -- 키워드 검색만 했으면 NULL
  embed_model TEXT,                   -- 임베딩 없이 했으면 NULL
  answer_json TEXT NOT NULL,          -- 답변 + 검증 결과 + 구조
  pinned INTEGER NOT NULL DEFAULT 0,  -- 중요 기록
  created_at TEXT NOT NULL
);

CREATE TABLE job_evidence (           -- 당시 근거를 통째로 스냅샷
  job_id INTEGER NOT NULL REFERENCES job(id),
  ord INTEGER NOT NULL,               -- 답변의 [n] 번호와 일치
  document_id INTEGER,                -- 지워졌으면 NULL 이 될 수 있음
  doc_title TEXT NOT NULL,            -- 당시 이름
  doc_sha256 TEXT NOT NULL,           -- 당시 파일        <- 8번 요구사항
  page INTEGER NOT NULL,
  heading_path TEXT,
  quoted_text TEXT NOT NULL,          -- 당시 원문 그대로 (검증 재현의 근거)
  chunk_id INTEGER                    -- 참고용 (사라질 수 있음)
);

CREATE TABLE job_turn (               -- 7번 "이어서 질문하기" 확장 자리
  job_id INTEGER NOT NULL REFERENCES job(id),
  ord INTEGER NOT NULL,
  role TEXT NOT NULL,                 -- user | assistant
  content TEXT NOT NULL
);

CREATE TABLE setting (key TEXT PRIMARY KEY, value TEXT NOT NULL);
```

**설계에서 중요한 세 가지**

1. **`job_evidence` 는 청크 id 만 저장하지 않고 원문을 통째로 복사합니다.**
   재색인·문서 교체·삭제가 일어나도 과거 기록이 온전합니다. 요구사항 8의 가장
   확실한 해법입니다. 기록을 열 때 `doc_sha256` 을 현재 문서와 비교해 안내합니다:

   > 이 답변은 2026-09-01 당시 등록되어 있던 자료를 기준으로 생성되었습니다.
   > 해당 자료는 이후 변경되었습니다. [현재 자료 보기]

   덤으로, **과거 답변의 숫자 검증을 나중에 다시 돌릴 수 있습니다** — v0.2 의
   문맥 대조가 생기면 옛 기록에도 적용할 수 있습니다 (5-5).

2. **같은 파일을 다시 등록하면 삭제가 아니라 개정입니다.** 해시가 다르면 새
   문서로 넣고 `revision_of` 로 잇습니다. 옛 문서는 검색 대상에서 빠지지만
   지워지지 않아서, 과거 기록의 원문 보기가 계속 됩니다.

3. **`embed_state` 와 `collection.embed_model` 이 NULL 을 허용합니다.**
   AI 없이 등록한 문서가 정상 상태로 존재할 수 있어야 하기 때문입니다 (2-12).

### 보존기간

`setting` 에 `retention_days`(기본 30). 앱 시작 시 `pinned = 0` 이고 기한 지난
job 을 지웁니다. 설정: 7 / 30 / 90 / 365 / 0(직접 삭제할 때까지).

## 8. 개인정보 · 외부 통신 검토 (요구사항 10)

### 8-1. 로컬에만 있는 것

원본 PDF 사본, 추출 텍스트, 청크, 임베딩, 작업 기록, 근거 스냅샷, 그리고
**LLM 추론 전부**. 업무자료 내용은 이 PC 를 벗어나지 않습니다.

### 8-2. 외부 통신을 구조적으로 막는다 ★ (검토 반영)

검사보다 차단이 낫습니다. **Tauri 의 CSP 로 WebView 에서 외부로 나가는 길을
아예 없앱니다.**

```jsonc
// tauri.conf.json
"app": {
  "security": {
    "csp": "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self' ipc: http://ipc.localhost http://127.0.0.1:11434; object-src 'none'; base-uri 'none'"
  }
}
```

이렇게 두면 **pdf.js 가 cMap 을 CDN 에서 받으려 해도 브라우저가 막습니다.**
설정 실수가 있어도 자료가 새어 나가지 않습니다. 그 위에:

- pdf.js 의 `cMapUrl` / `standardFontDataUrl` 을 **앱 내부 경로**로 지정하고
  cMap·표준 폰트를 번들에 포함합니다. 한국어 PDF 는 cMap 을 실제로 씁니다.
- Rust 쪽 HTTP 클라이언트는 **허용 호스트를 코드에서 제한**합니다
  (`127.0.0.1:11434`, 그리고 명시적 통신 두 곳만).

### 8-3. 명시적으로 필요한 통신 — 이것만 나갑니다

| # | 대상 | 언제 | 나가는 것 | 끌 수 있나 |
|---|---|---|---|---|
| 1 | `registry.ollama.ai` | 사용자가 **[AI 모델 설치]** 를 누를 때만 | 모델 이름만. **업무자료 아님** | 안 누르면 안 나감 |
| 2 | `github.com` / `objects.githubusercontent.com` | 앱 업데이트 확인 · 내려받기 | 현재 버전 정보 | **설정에서 끌 수 있음** |
| 3 | `127.0.0.1:11434` | 임베딩·답변 생성 | 업무자료 (⚠ 아래) | — |

> ⚠ 3번은 **이 PC 안**이지만 네트워크 요청은 맞습니다. 루프백이라 랜선을 뽑아도
> 됩니다. 다만 **같은 PC 의 다른 프로그램도 11434 포트에 접근할 수 있습니다.**
> 공용 PC 라면 알아 둘 일입니다.

이 셋 말고 **의도하지 않은 요청이 하나도 없다는 것을 실제로 시험합니다** (10-6).
이건 MVP 완료 조건입니다.

### 8-4. 저장에 관해 정직하게

- 업무자료는 `data.db` 안에 **평문**으로 들어갑니다. 학생 이름이 든 자료를
  넣으면 그 이름이 평문으로 남습니다. **암호화는 MVP 밖**입니다.
- 그러므로 **이 앱의 자료 폴더 자체를 개인정보 보관소로 취급**해야 합니다.
  설정 화면과 README 에 이 사실과 폴더 위치를 명시하고, 백업 파일도 같은
  주의가 필요하다고 적습니다.
- SQLite WAL/journal 은 앱 폴더 안에만 생깁니다. Rust 쪽에서 임시파일을 만들지
  않고, pdf.js 는 메모리에서 처리합니다.
- Windows 검색 인덱서가 `%APPDATA%` 를 훑을 수 있습니다 — 파일명 수준입니다.
- v0.2 선택지: SQLCipher 로 DB 암호화, 또는 BitLocker/EFS 안내.

- **P4b 에서 검색 정확도를 수치로 확정한 뒤에 P5(LLM)로 갑니다.** 검색이 나쁜데
  LLM 을 붙이면 원인을 구분할 수 없습니다.

## 10. 테스트 전략

기존 앱의 `npm run check:model` 방식(node 로 순수 함수를 검사)을 그대로 씁니다.

### 10-1. 순수 함수 단위 검사

| 대상 | 왜 |
|---|---|
| 문장 분할 | `1.` `제3조.` `2026. 3. 1.` 함정 (2-4) |
| 청크 경계·겹침 | 글자 오프셋이 새면 근거가 어긋남 |
| 오프셋 → 쪽 매핑 | 근거 표시의 심장 |
| 줄 재구성 · 표 블록 | 표 처리 |
| RRF 융합 | `w_vec = 0` 일 때 키워드 전용으로 떨어지는지 포함 |
| 인용 파싱 `[n]` | 검증층 |
| 숫자·날짜·조항 추출 | 검증층 |
| **숫자 검증 범위** | **인용된 청크 밖의 숫자를 통과시키지 않는지** (5-4) |
| 보존기간 계산 | 기록 삭제 |

### 10-2. 골든 셋 — 이 프로젝트에서 가장 중요한 시험

실제 업무자료로 만듭니다. **자료 성격을 셋으로 나눕니다** (확정):

| 유형 | 예 | 무엇을 재나 |
|---|---|---|
| ① 긴 운영 매뉴얼 | 늘봄학교 운영 매뉴얼 | 많은 쪽에서 정확한 곳을 집어내는가 |
| ② 숫자가 중요한 지원금·사업 지침 | 초3 이용권 운영지침 | 금액·대상·기간을 틀리지 않는가. **표 처리와 숫자 검증** |
| ③ 규정 해석이 중요한 회계·행정 지침 | 학교 회계 지침 | 조항을 정확히 찾고, 해석과 사실을 구분하는가 |

질문 30~50개 + **정답 근거(파일·쪽)** 를 CSV 로 만들고, 회귀 검사는
**LLM 답변이 아니라 검색 결과만** 채점합니다.

```
Recall@5     정답 쪽이 상위 5개 근거 안에 있는가   -> 목표 90% 이상
Precision@1  1위가 정답 쪽인가                     -> 목표 60% 이상
```

유형별로 따로 냅니다. ②의 수치가 낮으면 표 처리(2-2)를 손봐야 한다는 뜻입니다.

**키워드 전용(P4a)과 하이브리드(P4b)를 각각 잽니다.** 하이브리드가 키워드보다
나쁜 질문이 있으면 RRF 가중치를 조정할 근거가 됩니다.

이 골든 셋으로 조정할 것: 청크 크기, 겹침, RRF 가중치, 거부 임계값(2-7 ④).

### 10-3. 거부 시험 — 환각 측정

**자료에 없는 것이 확실한 질문 10개**를 골든 셋에 넣습니다.
(예: 늘봄 자료집에 "교원 성과상여금 지급 기준"을 묻기)

```
거부율   "확인할 수 없습니다" 로 답한 비율   -> 목표 100%
```

### 10-4. 숫자 검증 한계 시험 ★ (검토 반영)

5-5 의 A/B 예시를 **일부러 시험 자료로 만듭니다.**

```
근거:  A 대상: 25만원 / B 대상: 50만원
질문:  A 대상은 얼마입니까?
```

- 답이 맞으면 → 통과.
- 답이 "50만원"으로 틀리면 → **v0.1 의 숫자 검증은 이걸 못 잡는 것이 정상.**
  이 시험의 합격 기준은 "잡아내는 것"이 아니라 **"화면에 '검증 완료' 같은
  과장된 표현이 나오지 않는 것"** 입니다.
- v0.2 에서 문맥 창 대조를 넣으면 이 시험의 합격 기준이 "잡아내는 것"으로
  올라갑니다.

### 10-5. Rust 쪽

메모리 SQLite 로 마이그레이션·리포지토리 검사. 특히 **v1 → v2 마이그레이션 후
임베딩이 살아 있는가**, 그리고 **`embed_model` 이 NULL 인 자료집에서 검색이
깨지지 않는가**.

### 10-6. 오프라인 검증 — MVP 완료 조건 ★ (검토 반영)

**방법: 호스트 방화벽으로 앱의 아웃바운드를 전부 차단한 뒤 전 기능을 수행한다.**
루프백(127.0.0.1)은 방화벽 규칙에 걸리지 않으므로 Ollama 는 계속 됩니다.
따라서 **"외부 통신 없이도 전부 된다"를 결정적으로 확인**할 수 있습니다.

```powershell
# DocAid.exe 의 아웃바운드를 막는다 (검증용, 끝나면 지운다)
New-NetFirewallRule -DisplayName "DocAid-offline-test" -Direction Outbound `
  -Program "C:\Program Files\DocAid\DocAid.exe" -Action Block
```

| 3 | PDF 원문 보기 | 글자가 깨지지 않고 하이라이트가 맞음 |
| 4 | 낱말로 찾기 · 근거 찾기 | 결과 나옴 |
| 5 | LLM 질의 | 답변 생성 (Ollama 는 루프백) |
| 6 | 개발자도구 네트워크 탭 | **외부 호스트 요청 0건** |

**보조 확인** (더 촘촘하게):

- `Get-NetTCPConnection -OwningProcess <pid>` 로 앱 프로세스의 실제 연결을 봅니다.
  `127.0.0.1:11434` 외의 원격 주소가 있으면 실패.
- CSP 위반은 개발자도구 콘솔에 찍히므로, **콘솔에 CSP 위반이 하나도 없어야**
  합니다 (위반이 있다는 건 어딘가 외부로 나가려 했다는 뜻입니다).

**따로 구분해서 시험하는 "명시적으로 필요한 통신"** (8-3) — 방화벽 규칙을 지운
뒤 따로 확인합니다.

| 시험 | 확인할 것 |
|---|---|
| [AI 모델 설치] 누름 | `registry.ollama.ai` 로만 나감. 업무자료 내용이 요청 본문에 없음 |
| 업데이트 확인 | GitHub 으로만 나감. 설정에서 끄면 요청이 사라짐 |

이 두 가지는 **사용자가 버튼을 눌렀을 때만** 나가야 합니다. 앱 시작만으로 1번이
나가면 실패입니다.

### 10-7. 손으로 하는 시나리오

- 스캔 PDF · 200쪽 PDF · 표 위주 PDF · 한글 파일명 PDF · 암호 걸린 PDF
- **Ollama 를 한 번도 설치하지 않은 깨끗한 PC 에서 앱 설치 → 자료 등록 →
  낱말로 찾기 → 원문 보기까지 전부** ← 1-4 요구사항의 실물 확인
- 모델을 나중에 설치했을 때 "임베딩이 없는 문서 N개" 안내가 뜨고 채워지는가
- 같은 파일 재등록 / 내용이 바뀐 같은 이름 파일 재등록
- 등록 도중 취소 / 등록 도중 앱 종료
- 모델 다운로드 도중 네트워크 끊기 → 앱이 죽지 않고 1단계 기능이 유지되는가
- 자료집 삭제 후 과거 기록 열기
- **업데이트(구버전 → 신버전) 후 자료집·임베딩·기록이 그대로인가** ← 매 릴리스
- 앱 폴더를 다른 PC 로 복사해 이어 쓰기

기존 앱에서 쓴 UI Automation 자동 조작 방식을 업데이트 시험에 그대로 씁니다.

## 11. 정직하게 말해 두는 위험

1. **표가 많은 자료의 검색 품질.** 가장 큰 품질 위험입니다. 원문 보기가
   안전망이지만, 표 위주 자료집에서는 기대를 낮춰야 합니다. 골든 셋 유형 ②로
   실제 수치를 봅니다.

2. **숫자 검증은 부분 검증입니다.** 5-5 에 적은 A/B 문제를 v0.1 은 못 잡습니다.
   화면 문구가 이 한계를 정확히 전달하는지가 P5 의 합격 조건입니다.

3. **HWP 를 못 씁니다.** 실사용에서 바로 나올 이야기입니다. 당장의 우회는
   *한글에서 PDF 로 저장*이고, v0.2 최우선으로 HWPX 를 넣습니다.

4. **4B 모델의 해석 품질.** 검색은 임베딩이 하고 LLM 은 "찾아 준 근거를 읽고
   정리"만 하므로 4B 로도 검색 답변·요약은 쓸 만합니다. 다만 규정 해석은
   확실히 약합니다. 16GB 이상이면 `qwen3:8b` 를 권하고, 해석 결과에는
   "AI 해석" 배지를 붙여 신뢰 수준을 낮춰 표시합니다.

5. **임계값은 실제 자료 없이 못 정합니다.** 2-7 의 0.35/0.50 은 출발점일 뿐
   입니다. P4b 에서 실제 자료로 잽니다.
